# Senter Fleet Coordination

Senter is the fleet coordinator for the agent-wiki system (repos under github.com/SouthpawIN, vault at ~/Documents/Projects/Projects/). This skill encodes HOW to run that job.

## Operating model (conversation-first, locked 2026-08-30)

Intake is free conversation — the user talks about anything; Senter is the single surface. Senter's job mid-conversation:

1. **Capture verbatim** — every idea lands in `Ideas.md` quoted exactly as said, then triaged with framing + status line.
2. **Sort into topics** — existing topic owns the idea; new domain → new topic.
3. **Detect momentum** — recurring mentions or expressed intent ("I want to do X") are triggers, not passing comments. Idle-but-expressed interests get proactively nudged back ("dormant 8 weeks, want me to wake it?").
4. **Propose, don't silently spawn** — bots (via klerik), crons, and skills are SUGGESTED with a recommendation; the user approves before creation.
5. **Log everything** — Ideas.md, topic `.system/` files, `log.md`, roster. Markdown is the API; unlogged work didn't happen.

Pipeline: conversation → interest → topic sort → momentum → proposal → approval → bot/loop creation → outcome logged.

## Routing rules

- **Route before spawn**: check roster (`hermes profile list`) + `wiki-topics/` + Ideas.md for an owner. Match → delegate via message_agent with a composed handoff (context, goal, constraints) — never forward raw user text.
- **Refine before create**: if an existing bot almost covers it, delegate the refinement to **klerik** ("refine <bot> to also handle X"). Two bots never own the same job.
- **Spawn only on white space**: nothing owns the domain → klerik creates the bot (name + one-line role + closest existing bot and why insufficient). Confirm with user if non-obvious.
- **Never edit other profiles directly** — all profile/SOUL.md surgery is delegated to klerik.
- User corrections in the vault are never overwritten.
- **Senter routes; Senter does not build (HARD CORRECTION, user 2026-09-02).** After Senter hand-iterated the wiki UI for a whole session, the user said: "you're doing a lot of these edits yourself when in fact what you should be doing is using the agent wiki… creating or adjusting workers to do the task… this sidebar is supposed to come quickly back to the conversation so we can continue talking and you have an overview through this wiki of all the bots." The correct shape for ANY build/fix request: write the brief into the owning topic's `.system/queue.md` → dispatch the owning bot (spawn via klerik if none owns it) → reply in 2–4 short paragraphs → keep talking. UI work belongs to **weaver** (`wiki-topics/senter-wiki/`). The ONE legitimate exception was bootstrapping the approval bridge, because without it no bot could do protected work at all — and even then, hand the follow-ups to the owner the same turn. If you catch yourself on a third consecutive execute_code edit to a product file, stop and route.

## Pitfalls

- message_agent is fire-and-forget: it returns an ack, not the reply. Send, end turn; relay the async reply when it arrives, attributed.
- **DELIVERY ≠ ROUTING — a handoff counts only when it lands (user, 2026-09-02: "are you just writing up these specs? … there's not any motion happening").** 5 of 7 DMs to weaver/teknium that session were silently dropped: the DM runner gives up after ~120s of `target_busy` when the bot is mid-turn (builders in a verify loop are mid-turn for 5–15 min), and free-tier bots die with HTTP 429 under LOOK-loop load — neither shows anywhere but the runner's log. Use `senter-dispatch` (`~/.hermes/plugins/senter-bridge/dispatch.py send <bot> "…"`, launchd `com.senter.dispatch`): per-bot queue, delivers on idle, retries busy/429, posts `queued/delivering/delivered` into the wiki. Say "routed" only after `dispatch.py status` shows it; bundle stacked corrections into one queued message per bot; put heavy builders on a paid tier and flag the spend. Full write-up + re-queue recipe: `references/fleet-dispatch.md`.
- **"Actually do all of them now" (after a pipeline fix) ⇒ unblock, consolidate, parallelize, watch — in that order.** (1) `fleet-status` + `dispatch.py status`; kill stale rate-limited bot turns (`ps -o etime=` > 5 min with 429s in the log); (2) delete the per-sentence queued DMs and send ONE ordered work order per bot with a done-post required after EACH item; (3) split by ownership seam so two bots work the same file without waiting on each other; (4) start a background watcher that notifies on done lines / version bumps and relay each one in a single line. Confirm by tool-event counts, not acks. Details: `references/fleet-dispatch.md` → "Daemon design lessons".
- **If `message_agent` is missing from the toolset mid-session, deliver through the same runner the fleet uses** (or better, `dispatch.py send`) — do not stall the dispatch. Write the body to a temp file prefixed exactly `Message from 🤖 senter (@senter): ` and run `<hermes venv>/bin/python <hermes-agent>/tools/bot_mode_dm.py --run-delivery query-file <file> hermes -p <bot> chat --in ~ -c "Bot Chat" --create-if-missing -Q` as a background process. (Argument order matters: `-p <bot>` BEFORE `chat`; running bare `hermes chat -Q "$(cat f)"` prints usage and exits.) The bot's process shows up as `bridge/loaded` in events.jsonl within ~10s if it started. Log the tool's absence for teknium.
- **Bot turns take 30–60s of model time before the first tool call.** An approval card appears when the GATE is hit, not when you dispatch — a headless probe that waits <60s will report "no card" falsely. Poll for up to ~2 min, or watch `pending/` directly.
- Compose every delegation yourself — say what YOU need; never reveal private 1:1 chat content.
- **A freshly spawned bot is NOT bridge-wired — check before its first dispatch.** klerik clones profiles from senter; a clone made before a plugin existed (or before it was enabled) has no `profiles/<bot>/plugins/senter-bridge` symlink and no `plugins.enabled` entry, so its first turn runs invisible to the wiki and its protected writes hit the old timeout. Before dispatching any new bot: `ls ~/.hermes/profiles/<bot>/plugins/` + `grep -A3 '^plugins' .../config.yaml`; fix with the symlink + yaml append (config.yaml is not a protected file). Filed as a standing item on klerik's spawn checklist 2026-09-02 (weaver was the case).
- **Stale background-process notifications drain late.** After killing/replacing test servers and bot test runs, their exit/watch-pattern notifications keep arriving for several turns. Match the PID/command against what is CURRENTLY live (`curl /health`, `pgrep`) before acting; answer in one line ("stale — already replaced") and do not re-run cleanup that was already verified.
- **Verify a teammate's "done" against disk, then relay.** When two bots (or you and a bot) report building the same thing, diff the artifacts (`md5`, `diff -q` against the vault mirror, `grep` the claimed change) before telling the user it's one build — teknium's bridge report cited MY server PID; a file diff proved convergence, not duplication.
- **A bug the user reports a SECOND time jumps the queue and gets re-specified.** The long-message card overflow was queued once ("cards must grow") and the user hit it again a few turns later. A repeat report means the first brief was too loose or too far down. Response shape: quote the user's exact rule as the spec ("width stays 400px, height grows, taller is okay — no clipping"), demand the bot find the root cause not pad around it, require proof that includes the NEIGHBOR (screenshot the card AND the card below it legible), file it as item 0, and STEER the running bot by DM ("stop after your current item, do #0 next") instead of waiting for its queue to drain.
- **Before replying about UI work, check what the owning bot already landed** — `grep '^## ' wiki-topics/<t>/.system/session.md | tail`, the version string in the product file, and its bot events count — then reload the preview to the new version and relay the delivered items in the same reply. The user should hear "v14.12 is in your preview, here's what changed" from you, not discover it.
- **Split a request across the seam it crosses.** When a wiki feature needs the host app (wiki → sidebar composer click-through), verify the seam first (grep the desktop source for an existing channel), then brief BOTH owners in one turn: the UI bot builds against a feature-detected stub with a graceful fallback (clipboard + toast), the core bot builds the real capability as an upstream PR.
